# ADR-0005: The Chat Relay Is a Host This Project Operates

**Status:** Proposed. Recorded by the writer session on [#206](https://github.com/OKJ1105/evidence-first-rag/issues/206) from the repository owner's decision of 2026-09-25, recorded on [#205](https://github.com/OKJ1105/evidence-first-rag/issues/205), that the chat relay runs in this repository's Milestone 5 deployment. The owner's disposition on the pull request is the recorded human decision.

**Superseded in part** by [ADR-0006](0006-relay-spend-is-bounded-by-the-provider-workspace.md) (item 5, the spend bound).

**Date:** 2026-09-25

## Context

[ADR-0004](0004-mcp-surface-and-the-tool-result-boundary.md) made one MCP server the single new entry point and left the conversation to a host: "This repository owns no conversational loop." Its Consequences named the page that makes the goal's link — "a page whose backend calls the Messages API with `mcp_servers` set" — and placed it in the portfolio site's repository.

That placement does not survive the site's own design. The site's Blueprint fixes that it "makes no server-side calls", that its deployment holds "no secrets", and that rate limiting, CORS and cost control "live in the RAG repository" (its Sections 3.1 and 10.3). A backend that holds an Anthropic key is a server-side call holding a secret. The owner therefore decided on 2026-09-25 that the **relay** — the endpoint the site's chat calls, the only component holding the Anthropic key — runs in this repository's Milestone 5 deployment beside `/v1` and `/mcp`.

The Messages API's MCP connector runs the tool-call loop on Anthropic's side: the caller supplies `mcp_servers` and an `mcp_toolset` that references each server, and the response carries the model's text and `mcp_tool_use` / `mcp_tool_result` blocks. The toolset takes per-tool configuration, including disabling a tool. The connector is a beta (`mcp-client-2025-11-20`) and reaches the server over public HTTPS.

So this repository does not own a loop, and ADR-0004's sentence stands. But it now owns **the host's configuration**: which model runs, what it is told, how much it may write, and which tools it may call. ADR-0004 accepted three residual risks — host prose beyond the tool boundary, host-composed arguments, and a selection the host makes or bypasses — **because the host was someone else's**. With the host ours, the question each risk was accepted under changes.

## Decision

**The relay is a host this project operates. It adds no tool, no route on the runtime and no second source of facts. It uses its configuration to close deterministically what ADR-0004 could only instruct, and the page that renders it keeps model prose and evidence visibly apart.**

1. **What the relay is.** One HTTP endpoint in this deployment. It takes a person's messages and returns one Messages API response: the model's text blocks, and the `mcp_tool_use` / `mcp_tool_result` blocks unchanged. It calls the Messages API with `mcp_servers` naming this deployment's own `/mcp`, and nothing else. It never calls the runtime, `/v1` or the database itself; every fact it returns reached it as an `mcp-v0.1` tool result. It holds the Anthropic key and no database credential. Its exact request and response shape is fixed in a contract, `relay-v0.1`, drafted beside this ADR.

2. **The model may discover; only a person may select.** The relay's toolset **enables `discover_entity` alone** and disables `query_facts` and `select_candidate`. A candidate list reaches the page as a `mcp_tool_result` block. The page renders it under `api-v0.1` Section 4.6 obligation 3, restated for this surface by `relay-v0.1` as item 3 records, and a **person's click** sends the selection to `/v1/select` from the browser. This closes two of ADR-0004's residual risks on this page. **The selection is a person's act again**, verifiably so, because the model holds no tool that selects. **No fact reaches the page without a person's click**, because the model holds no fact tool — close to the "no fact tool, every fact through selection" alternative ADR-0004 item 4 named, taken here at the host rather than in `mcp-v0.1`. `mcp-v0.1` is not changed: other hosts still see three tools, and ADR-0004's residual risks stand for them exactly as accepted.

   **The one tool the model keeps still instructs it to use the two it does not have.** `mcp-v0.1` Section 4.4 fixes the served `discover_entity` description exactly, `MC-020` and `MC-025` assert it byte for byte, and this ADR changes nothing there, so this host's connector fetches that same text: "Use select_candidate with the person's choice", and "A `resolved` result names exactly one entity and may be used with query_facts directly." Neither tool is in this toolset. A model told to call a tool it does not hold either narrates a selection it cannot make or — the hazard this project exists for — completes the answer from its own weights. `relay-v0.1`'s registered system prompt therefore **supersedes those two sentences for this host**: the person completes the choice in the page, the model neither selects nor fetches facts, and its part ends at reporting the result it received. The rest of the description — a candidate list is not an answer, never supply a scope the person did not name, a negative status is a result — is unchanged and still binds. That the registered system prompt is consistent with the enabled toolset is part of `relay-v0.1`'s acceptance evidence, beside the toolset itself.

   **One outcome takes a different road, and the record differs with it.** A discovery that resolves outright (tiers 1–2, `entity-discovery-v0.1` Section 4.7) returns one reference and **no `candidate_set_id`**, and that contract says a `resolved` outcome "needs no selection": its reference is an ordinary argument to a `mvp-v0.1` route. On this page it is shown with its tier and matched text, and the **person's click** sends it to `/v1/query`. The resulting fact carries no `selection` record, because there was no choice among several to record; what it carries instead is the byte-exact match that made the resolution, in the discovery result the person saw before clicking. So the property is "no fact without a person's click", not "every fact carries a `selection` record", and this ADR claims only the first.

3. **Model prose is shown as the model's, beside the evidence and never as it.** The page renders the model's text blocks in a region labelled as the assistant's words, and renders every fact only from a `/v1/select` or `/v1/query` response the page itself received, verbatim and with its evidence, in a separate region. A `mcp_tool_result` on this surface carries candidates, candidate scopes, a `resolved` reference or a negative status, and **never a fact**, because the model holds no fact tool; widening the toolset would reopen this ADR. **This is where Charter Section 3.1 is reached.** "User-facing text is a rendering of validated data" was read by ADR-0004 as a claim about this system's own output, with host prose outside it. On a page this project serves, from a host this project configures, the model's prose is this system's user-facing text. This ADR does not claim that prose is a rendering of validated data — it is not, and cannot be made so. It amends Section 3.1 instead, and the amendment states the carve-out rather than leaving two rules over one paragraph: **Section 3.1's first two sentences govern this system's own rendered output; model prose on a surface this project operates is not such a rendering, and is permitted only when labelled as the model's and shown apart from the evidence, with a fact shown only from a tool or route result.** The system prompt tells the model to answer only from tool results and to say when it found nothing. That is an instruction and not a check; the check is that the page never presents the prose as the fact.

   **Those conditions bind through `relay-v0.1`, not through `api-v0.1` Section 4.6.** That section governs a client of `api-v0.1` Section 4.1 "and nothing more". The relay's page is not that client: it calls the relay for conversation and renders candidates out of `mcp_tool_result` blocks, so Section 4.6's obligations do not reach it as written. `relay-v0.1` therefore fixes the obligations on the relay's client itself, with its own acceptance evidence, exactly as Section 4.6 carries them for the Milestone 4 UI: a prose region labelled as the model's; a fact rendered only from a `/v1/select` or `/v1/query` response, verbatim and with its evidence; and a candidate list, a candidate scope and a negative status rendered under Section 4.6 obligations 1, 3, 4 and 5, restated there for this surface. Without that the Charter's permission would land in this repository and its conditions nowhere. **The other three obligations are accounted for, not dropped.** Obligation 2's "no prose that states a fact" where `rendered` is `null`, and obligation 7's "no summary", are displaced on this surface by the Section 3.1 carve-out and replaced by its labelling-and-separation conditions; obligation 2's "`rendered`, verbatim" still binds the evidence region, and obligation 7's "no reordering of rows or candidates" and "no value the response does not contain" are restated for it by `relay-v0.1`. Obligation 6 does not arise, because no tool on this surface calls the adapter and no `proposal` reaches the page.

4. **The residual risk that remains is arguments; scope is decided here rather than left open.** The model still composes `discover_entity`'s arguments — a term, a kind, and the four scope values. A wrong term or kind fails closed, as `api-v0.1` Section 4.6's prefill table already records. A fully specified scope matching no snapshot is `coverage_gap`.

   **An under-specified scope is the case item 2's mechanism cannot reach, and it is closed on the page instead.** `entity-discovery-v0.1` Section 4.3 sends it to `mvp-v0.1` Section 4.2 unchanged: `ambiguous`, with the candidate scopes from `TPL_SNAPSHOT_CANDIDATES_V1`, and no discovery template executed. That list reaches the model as an `mcp_tool_result`, and nothing in the toolset stops it re-calling `discover_entity` with one of the listed scopes — `discover_entity` is the one tool it must keep. A tier-1 `resolved` would come back for a snapshot nobody chose, and Charter Section 3.6's "explicit selection or abstention" would have been satisfied by a model's pick. Disabling a tool cannot close that; the page can. **A scope value the model takes from an `ambiguous` candidate list may not reach a rendered reference or a rendered fact without a person's pick.** The relay can check that byte-exactly in the blocks it already returns — an `ambiguous` result listing candidate scopes, followed by a `discover_entity` call carrying one of them — and the page then renders those candidate scopes as the person's pick, none defaulted and none preselected, which is `api-v0.1` Section 4.6 obligation 4's rule against an unverified scope value as a field default, applied to the one surface where the unverified value is a model's re-call rather than an adapter's proposal. The chosen scope is the person's act. **The check is over the whole conversation, not one response**: item 6 keeps the relay stateless, so `relay-v0.1` requires every request to carry the prior relay turns, `mcp_tool_use` and `mcp_tool_result` blocks included, exactly as the relay returned them. `relay-v0.1` fixes the check and carries its acceptance evidence. The system prompt also tells the model to stop at an `ambiguous` result; as in item 3, that is the instruction and this is the check.

   **What stays accepted** is a scope value the model supplies from the person's own words — transcription, as the prefill table's `term` row is — and one it invents that happens to name a real snapshot. The second is the narrowed risk: the person sees that scope in the candidate before choosing, so a scope is **shown to a person before any fact is produced**, which ADR-0004 item 2 could not say of an arbitrary host. The risk is accepted in that form.

5. **Cost and abuse are bounded by the relay, not only by alerts.** The endpoint is unauthenticated, because the goal is a link a reader opens. So the relay enforces caps a runaway cannot pass: a request-rate limit per client, a turn limit per conversation, a fixed `max_tokens`, and a **daily ceiling past which it refuses** until the next day. The Azure budget alert (8,000 JPY/month, [#205](https://github.com/OKJ1105/evidence-first-rag/issues/205#issuecomment-5829415863)) and the Anthropic Console usage limit are backstops. They notify or stop at the provider, and neither is the design. *(Superseded for the spend bound by [ADR-0006](0006-relay-spend-is-bounded-by-the-provider-workspace.md) (#249): the workspace spend limit is the spend bound, so this item's lead sentence now holds for abuse and not for monthly cost; the relay's caps stay, and the Azure budget alert remains a backstop.)* The numbers are fixed in `relay-v0.1` and the deployment contract.

6. **What the relay records.** A person's messages are sent to Anthropic; that is the point of the relay, and the page says so before the first message. The relay stores no message text and logs no message text. Its logs carry counts, latencies, the tools called and the statuses returned — what Charter Section 9's "latency/error metrics" and failure classification need, and nothing a reader typed. A privacy-safe feedback workflow remains Charter Section 9's "when real users exist" item, and it is not started here.

## Alternatives considered

**The relay in the portfolio site's repository**, as ADR-0004 placed it. Rejected on the site's own Blueprint: it would add the site's first secret and first server-side call, and it would put cost control somewhere other than where the site's design says it lives.

**Give the model all three tools**, as any external host has them. Simpler, and consistent with every other host. Rejected because this is the one host where the two sharpest residual risks can be closed at zero contract cost, and leaving them open on the project's own page would present accepted risks as design.

**An owned conversational loop** — ADR-0004's first alternative. Still not needed. The Messages API runs the loop, and item 2 obtains the property the owned loop was wanted for, person-made selection with every fact carrying its record, from configuration.

**Authentication for readers.** Rejected for the link's purpose: a reviewer opening a link will not create an account. Item 5's caps are the substitute, and their numbers are reviewable.

## Consequences

- **Charter Section 3.1** gains a carve-out, citing this ADR: its first two sentences govern this system's own rendered output, and model prose on a surface this project operates is not such a rendering — it is permitted only labelled as the model's and apart from the evidence, and a fact is shown only from a tool or route result. **Section 7's "general-purpose chat assistant" non-goal is untouched**: the model holds one tool over a registered set of synthetic entities, and the system prompt confines it there.
- **Charter Sections 3.3 and 1.1 are read and are not edited, and the reading is recorded here because the premise ADR-0004 read them under has changed.** ADR-0004's Consequences left both unedited on the stated ground that "text a host model writes beyond the tool boundary is outside both claims". On this page that ground is gone, so each sentence needs its reading stated rather than inherited. **Section 3.3.** Of its six prohibitions, the four ADR-0004 item 2 called unavailable because no tool offers the act remain unavailable here; "silently resolve ambiguous entities", which ADR-0004 moved to the caller, is closed on this page by item 2's toolset and item 4's check; and the sixth, "infer missing engineering facts", is the one that remains. It still binds the model this project configures, and item 3 is candid that nothing in the relay prevents the act: the registered system prompt instructs against it and the page's separation keeps the sentence from being read as the fact, and neither is a check on the prose. **The permission Section 3.1 now carries is a permission to display, not a licence to infer.** Labelled prose shown apart from the evidence is permitted; an inference the prose contains stays prohibited and stays undetectable here. That is ADR-0004 item 2's residual risk, **re-accepted under the changed premise** — on the ground that the changed premise takes no mitigation away and adds three ADR-0004 had none of, each with `relay-v0.1` acceptance evidence: the labelling, the separation, and a fact rendered only from a tool or route result. The owner's record for the re-acceptance is the owner's decision of 2026-09-25 on [#206](https://github.com/OKJ1105/evidence-first-rag/issues/206#issuecomment-5828343795), where the owner chose it over amending Sections 3.3 and 1.1 or showing no model prose, together with the owner's disposition on this pull request. **Section 1.1.** Its criterion is about the outcome a registered task returns: the relay returns each tool result unchanged and the page renders a negative status as itself, so `not_found` and `coverage_gap` are still "the expected explicit negative outcome", and labelled prose beside such a result is not "a plausible unsupported answer" returned instead of it. It becomes one exactly when a surface presents prose as the result, which item 3's conditions forbid and `relay-v0.1`'s acceptance evidence covers. **So the case is settled for that contract's drafter rather than left open both ways:** a `not_found` discovery result (`DX-009`'s shape) shown beside a plausible model sentence naming a signal is permitted when the sentence is labelled as the model's, shown apart, and the `not_found` is rendered as the result; `relay-v0.1` may neither require the relay to suppress or rewrite the prose nor permit the page to render it as the answer. That a reader credits the sentence anyway is the standing hazard the last bullet names.
- **ADR-0004 stands.** No repository-owned loop; `mcp-v0.1` unchanged; its residual risks stand for external hosts. Its Consequences sentence placing the page in the portfolio repository is superseded for the **relay**, while the **page** still lives there.
- **`relay-v0.1`** is the next contract: the endpoint, its request and response, the toolset configuration of item 2, the system prompt as a fixed registered text (as `mcp-v0.1` fixes tool descriptions), including the supersession item 2 records of the two `discover_entity` description sentences that name the disabled tools, the caps of item 5, the refusals, and **the obligations on the relay's client** that item 3 hands it — a prose region labelled as the model's; a fact rendered only from a `/v1/select` or `/v1/query` response, verbatim with its evidence; candidate lists, candidate scopes and negative statuses under `api-v0.1` Section 4.6 obligations 1, 3, 4 and 5 restated for this surface; and item 4's check on a scope taken from an `ambiguous` candidate list. Its acceptance evidence covers each: that the toolset sent to the API enables `discover_entity` only, that the registered system prompt is consistent with that toolset, and that a scope taken from an `ambiguous` candidate list reaches no rendered reference or fact without a person's pick — **including across turns**: an `ambiguous` result in an earlier relay response, and a `discover_entity` call carrying one of its candidate scopes in a later one.
- **The deployment contract** carries the relay's identity (it alone reads the Anthropic key from Key Vault, and it holds no database credential), **and the `/v1` side of the page's calls**: the cross-origin allowlist for the site's origin on `/v1/select`, `/v1/query` and `/v1/discover`, and what bounds those unauthenticated routes. Item 5's caps are the relay's, because only the relay spends per call; `/v1` spends nothing per call and is bounded by the deployment's fixed cost, its read-only grants and its statement timeout, which the deployment contract states.
- **The portfolio site** changes its demo from calling the RAG API directly to calling the relay for conversation, and `/v1/select` or `/v1/query` for a person's choice, all from the browser, still holding no secret. That is the site repository's slice, against `relay-v0.1`.
- **The standing hazard is item 3's.** A model can still write a wrong sentence beside a right fact. The page's separation is what keeps it from being read as the fact, and observed use is the evidence for whether that separation holds.
