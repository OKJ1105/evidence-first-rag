# ADR-0004: An MCP Surface as the Single New Entry Point, and the Tool-Result Boundary

**Status:** Proposed. Recorded by the writer session on [#197](https://github.com/OKJ1105/evidence-first-rag/issues/197) from the repository owner's decision on [#169](https://github.com/OKJ1105/evidence-first-rag/issues/169) (2026-09-22); the owner's disposition on the pull request is the recorded human decision the [Project Charter](../PROJECT_CHARTER.md) status line requires.

**Date:** 2026-09-22

## Context

Milestones 1 to 3 are accepted. Milestone 4 delivered the HTTP surface ([api-v0.1](../contracts/api-v0.1.md)), a page over it, and a single-command local stack (#192). The page was rebuilt once (#195, #196) so that a negative result is rendered as the result it is.

The owner then used the rebuilt page and recorded the registered acceptance condition of #195 as **fail**: the page satisfies every `api-v0.1` Section 4.6 obligation and still requires `entity_kind` and the four scope dimensions before a person has any reason to know them. The form is a correct rendering of the contracts and is not a surface a reader can use unaided. That record is the input the #169 decision point asked for, and the owner took Path B.

Three facts bear on what replaces the form as the entry point.

**The industry converged on coexistence, and on letting the host orchestrate.** No system in the survey the owner requested replaced its form with a conversational surface; the ones surveyed run both over one governed definition layer (recorded on #195). Where a conversational surface exists, the tool provider ships a server and the host runs the loop: OpenAI's Apps SDK is an MCP server plus a widget, tested through ChatGPT's developer mode and distributed through ChatGPT ([primary source read](https://github.com/openai/openai-apps-sdk-examples)); Anthropic's Messages API connects to a remote MCP server server-side, runs the tool-call loop itself, and returns `mcp_tool_use` and `mcp_tool_result` blocks in the response ([primary source read](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)); Claude custom connectors take a server URL from the person (help-centre summary only; the page could not be fetched from the writer's environment). Building a conversational loop of one's own is the minority path, taken where a host cannot be trusted with the loop.

**Charter Section 3.3 fixes a boundary an MCP surface crosses.** "Database rows, fixture contents, and evidence bundles are not sent to an external model unless a separately reviewed ADR changes this boundary." An MCP tool returns its result to whatever model called it. This is that ADR.

**The invariant this repository exists for ends at the tool boundary when the host owns the loop.** The record on #169 (2026-09-21) states it: an MCP server returns tool results and controls nothing about what the host's model then writes. The failure that leaves open has a name — a host answering from its own weights when the tool returned `not_found` — and the only place it can be closed deterministically is a loop this repository owns. The owner weighed that against the cost of owning a loop and accepted the risk, on the record.

## Decision

**One MCP server, over HTTP, exposing the existing routes as tools, is the single new entry point. This repository owns no conversational loop. The Charter Section 3.3 boundary moves to the tool result. The invariant is guaranteed at the tool boundary and not beyond it.**

Six things follow, and each is a consequence of that decision rather than a separate one.

1. **What the tools are.** One tool per existing route, with one exclusion — `entity_selection` is not exposed, for the reason item 4 gives — each returning the route's result unchanged: the `mvp-v0.1` or `entity-discovery-v0.1` result, with its `evidence_bundle`, `source_trace`, `limitations` and, where the contract supplies one, `rendered`. The exact tool set, names, argument schemas and registered cases are fixed in a contract, `mcp-v0.1`, drafted after this ADR's disposition. The registered cases are equalities — the tool's result is the API's result for the same request — over every outcome the exposed routes already register, so the tool surface adds no outcome and no evidence shape of its own.

2. **What crosses the boundary.** Everything a tool result carries is returned to the host model. Fixtures are `SAMPLE_*` throughout (Charter Section 11), so nothing confidential crosses; what crosses is the reasoning surface Section 3.3 kept off the model. What moves is that one sentence and nothing else in Section 3.3: all six of its prohibitions stand unchanged — the host model cannot write SQL, select arbitrary tables or columns, infer a missing engineering fact, silently resolve an ambiguous entity, create a new route or contract at runtime, or judge conformance of its own output — because no tool offers any of those, and the one tool that would have offered the fourth is the one item 4 excludes. The tool set is the allowlist.

3. **Where the invariant ends, stated so it is not overclaimed.** Every tool returns a result the contracts govern; a negative result is returned as itself, never retried or rephrased inside the tool. That is the guarantee. What the host model writes afterwards is the host's output, not this system's, and this repository does not claim it. The mitigation — not a guarantee, and not everywhere — is that where the contract supplies a `rendered` sentence, the tool result's text is that sentence with its resolved scope beside it, so a host that quotes keeps the source. **It reaches `mvp-v0.1` results only.** [api-v0.1](../contracts/api-v0.1.md) Section 4.2 fixes `rendered` as `null` for every `entity-discovery-v0.1` result, because that contract defines no renderer and the surface does not invent one; so the discovery tool returns evidence and scope with no sentence to quote — and those are the `candidates`, `ambiguous`, `not_found` and `coverage_gap` outcomes where the hazard above is sharpest. `mcp-v0.1` is not expected to close that gap: a renderer invented at the tool boundary would be a second representation of a result whose contract has none, which the equality cases in item 1 forbid. The residual risk there is unmitigated and stands as accepted. The owner's acceptance of the residual risk, mitigated and unmitigated alike, is the #169 record of 2026-09-22.

4. **Decision A on #169 is amended for discovery, and `entity_selection` is not exposed as a tool.** Decision A's condition — "the surface itself never issues a discovery request on a caller's behalf" — was written for a page under a person's hand, and it holds there. A host model calling tools *is* the caller, and it may chain discovery after a `needs_entity_discovery` result, or try a second `entity_kind`, on its own. **That amendment reaches discovery and stops there.** It cannot reach selection, because selection is not this ADR's to move: [entity-discovery-v0.1](../contracts/entity-discovery-v0.1.md) is `Accepted`, its Section 4.8 says a selection is "never made by a model" — citing Charter Section 3.3's prohibition on silently resolving an ambiguous entity — its Section 4.12 says "No model ranks, selects, or judges", and its Section 1 forbids weakening an obligation at the contract layer. Nor could the tool boundary detect the breach: Section 4.8's seven steps verify the candidate *list* and never who chose from it, so a model-made selection would pass all seven and return true facts carrying the explicit-selection `limitations` entry — an evidence structure asserting a person's act the runtime cannot verify, which is what [#17](https://github.com/OKJ1105/evidence-first-rag/issues/17) rule 8 forbids. **So there is no selection tool.** A `candidates` result is terminal at the tool boundary: the host reports the list as a list, and the selection stays a person's act on the `/v1` surface, where [api-v0.1](../contracts/api-v0.1.md) Section 4.6 point 4 requires an explicit act naming one listed rank. The three orchestrator prohibitions Decision A carries then bind the tool definitions rather than a surface: no tool selects a candidate where more than one exists — none can, because none selects at all; a candidate list is returned typed as a candidate list, not as a fact; and a negative result is a result, with no tool that "tries something else". A tool cannot offer what its contract refuses, and here that is achieved by not defining the tool rather than by trusting a check the contract's steps do not make.

5. **The Thin LLM Adapter leaves the public path.** `mvp-v0.1` Section 4.6's adapter chose a route and extracted arguments from natural language. A host model choosing a tool does the same work, so `/v1/ask` and its `proposal` key are no longer the path a reader is directed to. This ADR does not remove them: that is an `api-v0.1` Section 10 amendment, its own slice. Milestone 2's acceptance record stands as the comparison it was, and the adapter remains available for evaluation.

6. **TSV export leaves Milestone 4.** The #169 decision-point record (2026-09-16) set Path B as "an ADR under Charter Section 10 moving TSV export out of Milestone 4 — to a later milestone or out of scope — with its reason". The reason is the one that record anticipated: the claim an export makes indirectly — that every value is traceable — is made directly by the evidence each tool result carries, and Charter Section 3.5 says to wait for a measured need. Export moves out of scope until one exists. `export-v0.1` (#159) stays `Proposed` and is not withdrawn.

## Alternatives considered

**A conversational surface this repository owns.** A loop in this repository, with the model writing only clarifying questions and every fact rendered from the runtime's own `rendered` string, would keep the invariant enforceable end to end — the guarantee an exported server cannot give. Rejected on cost and on the survey: it is three to five slices of contract, loop and transcript UI against one or two for a server, it is the minority pattern, and the same tool definitions serve both, so it can be added later without discarding anything if observed use shows the residual risk being realised. The owner's stated reason (#169): the orchestration would become the main body of work, and it is not what this repository is trying to show.

**Keep improving the form.** The #195 slice was exactly this, chosen because it was the cheapest test, and its registered condition failed. A second iteration would be spent against the same finding: the form requires knowledge the response cannot supply.

**Export the server and keep the page as the primary entry.** Coexistence is what the survey found, and the page and the API are kept. But the goal names a link a reader opens, and the owner's own use established that the page is not the surface that satisfies it. The page stays; it is no longer what the README points a reader at first.

## Consequences

- **Charter text.** One sentence appended to Section 3.3 citing this ADR for the boundary change, and a parenthetical on the Milestone 4 export deliverable in Section 9. Section 6's deferred list already names "conversational and streaming adapters" and "UI"; an MCP surface is a route-and-result surface under the [Contract Shape Framework](../contracts/README.md) Section 8 row "Route and result schemas for the post-Milestone 1 API" and needs no new deferred entry. Section 7's non-goal "a general-purpose chat assistant" is untouched: a fixed, one-tool-per-exposed-route server over fixed SQL is not one, and this ADR gives it no way to become one.
- **The Milestone 4 gate item that judged the export closes with it.** Charter Section 9's Milestone 4 gate reads "exported values are derived from the normalized runtime result"; [api-v0.1](../contracts/api-v0.1.md) Section 8 assigns that item — `G1` — to `export-v0.1`, which is not in this tree and is served by no route. Moving the deliverable out of scope leaves that item with no deliverable, no owning contract and no evidence, so it closes with the deliverable rather than standing unmet: the Milestone 4 acceptance record cites this ADR for it instead of recording a fail or dropping it silently. `G2` and `G3`, which `api-v0.1` Section 8 owns, are unaffected. Restoring the export restores the gate item with it.
- **The `mcp-v0.1` contract** is the next slice, under the [Contract Shape Framework](../contracts/README.md), with the line budget #169 Decision B set. Its acceptance evidence is the equality cases in item 1 above; it defines no `entity_selection` tool, and its Section 9 carries the reading of Decision A this ADR amends and the reason selection is excluded from it.
- **`api-v0.1` Section 10** is amended in its own slice to retire `/v1/ask` and `proposal` from the public route table. The page's Ask panel goes with it; the discovery and selection panels stay.
- **Milestone 4 closes** on the acceptance record, which states #195's fail, #193's registered-but-unrunnable rows, and this ADR's Path B honestly. **Milestone 5** deploys the same runtime with the MCP endpoint beside `/v1`; the Milestone 5 gate's "no second schema, fixture meaning, SQL-template behavior, or fallback runtime" is what makes the equality cases in item 1 the right acceptance evidence.
- **The link.** The Milestone 4 record on #169 (2026-09-21) placed "the MCP question" after Milestone 5 because "a host-configured MCP server is not a link". This ADR supersedes that ordering, and the reason is the primary source above: a page whose backend calls the Messages API with `mcp_servers` set is a link, and its response carries the tool results as typed blocks the page can render beside the model's text. That page belongs to the portfolio site's repository and is named here only so the goal's link is accounted for. Readers with a Claude or ChatGPT client add the server as a connector; readers with neither read a recorded transcript in the README.
- **The standing hazard is the one item 3 names**, and it is a hazard of the host, not of this runtime. Observed use is the evidence for whether it is realised; if it is, the owned-loop alternative above is the recorded next step, and nothing built under this ADR is discarded by it.
