# ADR-0004: An MCP Surface as the Single New Entry Point, and the Tool-Result Boundary

**Status:** Proposed. Recorded by the writer session on [#197](https://github.com/OKJ1105/evidence-first-rag/issues/197) from the repository owner's decision on [#169](https://github.com/OKJ1105/evidence-first-rag/issues/169) (2026-09-22); the owner's disposition on the pull request is the recorded human decision the [Project Charter](../PROJECT_CHARTER.md) status line requires.

**Date:** 2026-09-22

## Context

Milestones 1 to 3 are accepted. Milestone 4 delivered the HTTP surface ([api-v0.1](../contracts/api-v0.1.md)), a page over it, and a single-command local stack (#192). The page was rebuilt once (#195, #196) so that a negative result is rendered as the result it is.

The owner then used the rebuilt page and recorded the registered acceptance condition of #195 as **fail**: the page satisfies every `api-v0.1` Section 4.6 obligation and still requires `entity_kind` and the four scope dimensions before a person has any reason to know them. The form is a correct rendering of the contracts and is not a surface a reader can use unaided. That record is the input the #169 decision point asked for, and the owner took Path B.

Three facts bear on what replaces the form as the entry point.

**The industry converged on coexistence, and on letting the host orchestrate.** No system in the survey the owner requested replaced its form with a conversational surface; the ones surveyed run both over one governed definition layer (recorded on #195). Where a conversational surface exists, the tool provider ships a server and the host runs the loop: OpenAI's Apps SDK is an MCP server plus a widget, tested through ChatGPT's developer mode and distributed through ChatGPT ([primary source read](https://github.com/openai/openai-apps-sdk-examples)); Anthropic's Messages API connects to a remote MCP server server-side, runs the tool-call loop itself, and returns `mcp_tool_use` and `mcp_tool_result` blocks in the response ([primary source read](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)); Claude custom connectors take a server URL from the person (help-centre summary only; the page could not be fetched from the writer's environment). Building a conversational loop of one's own is the minority path, taken where a host cannot be trusted with the loop.

**Charter Section 3.3 fixes a boundary an MCP surface crosses.** "Database rows, fixture contents, and evidence bundles are not sent to an external model unless a separately reviewed ADR changes this boundary." An MCP tool returns its result to whatever model called it. This is that ADR.

**The invariant this repository exists for ends at the tool boundary when the host owns the loop.** The record on #169 (2026-09-21) states it: an MCP server returns tool results and controls nothing about what the host's model then writes. The failure that leaves open has a name — a host answering from its own weights when the tool returned `not_found` — and the only place it can be closed deterministically is a loop this repository owns. The owner weighed that against the cost of owning a loop and accepted the risk, on the record.

## Decision

**One MCP server, over HTTP, exposing the existing routes as tools, is the single new entry point. This repository owns no conversational loop. The Charter Section 3.3 boundary moves to the tool result. The invariant is guaranteed at the tool boundary and not beyond it.**

Six things follow, and each is a consequence of that decision rather than a separate one.

1. **What the tools are.** One tool per existing route except `/v1/ask` (item 5), each returning the route's result unchanged: the `mvp-v0.1` or `entity-discovery-v0.1` result, with its `evidence_bundle`, `source_trace`, `limitations` and, where the contract supplies one, `rendered`. The exact tool set, names, argument schemas and registered cases are fixed in a contract, `mcp-v0.1`, drafted after this ADR's disposition. The registered cases are equalities — the tool's result is the API's result for the same request — over every outcome the routes already register, so the tool surface adds no outcome and no evidence shape of its own.

2. **What crosses the boundary, and which prohibition moves with it.** Everything a tool result carries is returned to the host model. What crosses is the reasoning surface Section 3.3 kept off the model, and the exception is bounded by its premise: the approved data scope is the synthetic `SAMPLE_*` fixtures Charter Section 11 requires, so nothing confidential crosses; a non-synthetic data scope would reopen this ADR, not inherit it. Section 3.3 lists six prohibitions. Four are unchanged because no tool offers the act: the host model cannot write SQL, select arbitrary tables or columns, create a route or contract at runtime, or judge conformance of its own output — the tool set is the allowlist. One, "infer missing engineering facts", is the residual hazard item 3 names: a tool cannot prevent it, and it is accepted there. **One moves: "silently resolve ambiguous entities."** Item 4 records where it goes and what remains verifiable.

   **One permission loses its check as well, and this ADR records that rather than the evidence direction alone.** Section 3.3 permits a model to "extract explicitly stated arguments", and `api-v0.1` Sections 4.3 and 4.6 make that checkable: a scope value may become a default only where it appears verbatim in the person's request, because a scope the person never named yields *true facts about the wrong snapshot* with nothing in the evidence saying where the scope came from. At the tool boundary the host model composes every argument, and no equivalent of the verbatim gate exists — the tool receives values, not the person's words. The runtime still refuses a scope that does not exist and still records the scope it used in `resolved_scope` and `bound_parameters`, so the error is visible in the evidence but not prevented. `mcp-v0.1` states in every tool description that scope values are the person's own words, which is an instruction to the host and not a check. This is a residual risk of the same kind as item 3's, and it stands as accepted under the same record.

3. **Where the invariant ends, stated so it is not overclaimed.** Every tool returns a result the contracts govern; a negative result is returned as itself, never retried or rephrased inside the tool. That is the guarantee. What the host model writes afterwards is the host's output, not this system's, and this repository does not claim it. The mitigation — not a guarantee, and not everywhere — is that where the contract supplies a `rendered` sentence, the tool result's text is that sentence with its resolved scope beside it, so a host that quotes keeps the source. **It reaches `mvp-v0.1` results only.** [api-v0.1](../contracts/api-v0.1.md) Section 4.2 fixes `rendered` as `null` for every `entity-discovery-v0.1` result, because that contract defines no renderer and the surface does not invent one; so the discovery tool, and the selection tool when it refuses rather than dispatches, return evidence and scope with no sentence to quote — and those are the `candidates`, `ambiguous`, `not_found` and `coverage_gap` outcomes where the hazard above is sharpest. `mcp-v0.1` is not expected to close that gap: a renderer invented at the tool boundary would be a second representation of a result whose contract has none, which the equality cases in item 1 forbid. The residual risk there is unmitigated and stands as accepted. The owner's acceptance of the residual risk, mitigated and unmitigated alike, is the #169 record of 2026-09-22.

4. **Decision A on #169 is amended, and the selection tool is exposed with its provenance stated honestly.** Decision A's condition — "the surface itself never issues a discovery request on a caller's behalf" — was written for a page under a person's hand, and it holds there. A host model calling tools *is* the caller, and it may chain discovery after a `needs_entity_discovery` result, or try a second `entity_kind`, on its own. Two of the three orchestrator prohibitions that record carries bind the tool definitions and need no loop: a candidate list is returned typed as a candidate list, not as a fact; and a negative result is a result, with no tool that "tries something else".

   **The third — no selection on the person's behalf — cannot be bound to a tool definition, and this ADR says so rather than claiming it.** `entity-discovery-v0.1` Section 4.8 says a selection "is never made by a model" and comes "from a person, or from an API caller relaying a person's choice"; Section 4.12 makes it an obligation. Its trust mechanism, Section 4.8 step 4, verifies **the list** — the runtime re-derives the candidate set and refuses a stale digest — and verifies nothing about who chose from it. That is already true of `/v1/select` for every caller: a request assembled without a person passes every step today. The selection tool is `/v1/select`'s equal, with the same argument shape and the same seven steps, and the host model is the API caller the contract names. This ADR reads "never made by a model" and "no model ranks, selects, or judges" as binding **this system's own models** — the adapter and anything inside the runtime — which they still do. For the host, the obligation to relay a person's choice is stated in the tool's description and is not enforceable here, exactly as item 3 says of prose. A host that selects without a person produces true facts about an entity nobody chose, carrying a `limitations` entry that today reads as "an explicit user selection" — a provenance claim the runtime cannot verify, which #17 rule 8 forbids it to assert. **So `mcp-v0.1` carries one obligation:** the entry's wording is patched to what the runtime does verify — the candidate set, its digest and count, and that a caller selected from it — and never to who chose. That is a patch to `entity-discovery-v0.1` Section 7 under its Section 10, the owner's to record on that contract's own slice; it weakens no check, because no check ever verified the person. What this ADR does not do is make a model-made selection detectable. That residual risk stands beside item 3's under the same #169 record, and it is the "silently resolve ambiguous entities" prohibition item 2 names as moved: the runtime still resolves nothing, and Charter Section 7's "automatic resolution of ambiguous entities without an approved policy" is met by this being the policy — resolution by the caller, recorded as the caller's.

   **Exposing the selection tool does not make it the only road from a candidate list to a fact, and excluding it would not have made a `candidates` result terminal either.** A candidate carries its four scope dimensions and its lookup key, and `entity-discovery-v0.1` Section 4.8 itself calls such a reference "an ordinary fully-scoped argument to a `mvp-v0.1` route". A host that reads rank 1 out of a `candidates` result and calls a fact tool with it gets true facts about the entity it picked, with no `selection` record, no `candidate_set_id`, no candidate count, and no explicit-selection `limitations` entry — less evidence than the selection tool returns for the same choice. The runtime cannot tell that reference from one a person typed, so no tool definition closes this. What the evidence still carries on that path is `resolved_scope` and `bound_parameters` verbatim, so *what* was answered stays traceable; what is lost is the record that a choice was made among several. The tool descriptions direct the host through the selection tool, which is an instruction and not a check. This is the third residual risk this ADR records, beside item 3's prose and item 2's arguments, and it stands as accepted under the same record. One deterministic alternative exists and is named for the `mcp-v0.1` slice rather than decided here: expose no fact tool and reach every fact through selection, so that every fact the MCP surface returns carries a `selection` record — at the cost that a `resolved` discovery outcome, which needs no selection, would then have no tool to complete it without a contract change.

5. **The Thin LLM Adapter leaves the public path.** `mvp-v0.1` Section 4.6's adapter chose a route and extracted arguments from natural language. A host model choosing a tool does the same work, so `/v1/ask` and its `proposal` key are no longer the path a reader is directed to. This ADR does not remove them: that is an `api-v0.1` Section 10 amendment, its own slice. **`/v1/ask` is not exposed as a tool**, and `mcp-v0.1` registers that exclusion: a tool over it would put a second model in the chain, and the `proposal` key — an adapter's unverified output — would cross the boundary as if it were a result, which items 2 and 3 do not account for and this ADR does not admit. Milestone 2's acceptance record stands as the comparison it was, and the adapter remains available for evaluation.

6. **TSV export leaves Milestone 4.** The #169 decision-point record (2026-09-16) set Path B as "an ADR under Charter Section 10 moving TSV export out of Milestone 4 — to a later milestone or out of scope — with its reason". The reason is the one that record anticipated: the claim an export makes indirectly — that every value is traceable — is made directly by the evidence each tool result carries, and Charter Section 3.5 says to wait for a measured need. Export moves out of scope until one exists. `export-v0.1` (#159) stays `Proposed` and is not withdrawn.

## Alternatives considered

**A conversational surface this repository owns.** A loop in this repository, with the model writing only clarifying questions and every fact rendered from the runtime's own `rendered` string, would keep the invariant enforceable end to end — the guarantee an exported server cannot give. Rejected on cost and on the survey: it is three to five slices of contract, loop and transcript UI against one or two for a server, it is the minority pattern, and the same tool definitions serve both, so it can be added later without discarding anything if observed use shows the residual risk being realised. The owner's stated reason (#169): the orchestration would become the main body of work, and it is not what this repository is trying to show.

**Keep improving the form.** The #195 slice was exactly this, chosen because it was the cheapest test, and its registered condition failed. A second iteration would be spent against the same finding: the form requires knowledge the response cannot supply.

**Export the server and keep the page as the primary entry.** Coexistence is what the survey found, and the page and the API are kept. But the goal names a link a reader opens, and the owner's own use established that the page is not the surface that satisfies it. The page stays; it is no longer what the README points a reader at first.

## Consequences

- **Charter text.** One sentence appended to Section 3.3 citing this ADR for the boundary change — bounded by Section 11's synthetic data scope, and naming the prohibition item 4 moves — and, in Section 9, a parenthetical on the Milestone 4 export deliverable and the same on the gate item that judged it. Section 6's deferred list already names "conversational and streaming adapters" and "UI"; an MCP surface is a route-and-result surface under the [Contract Shape Framework](../contracts/README.md) Section 8 row "Route and result schemas for the post-Milestone 1 API" and needs no new deferred entry. Section 7's non-goal "a general-purpose chat assistant" is untouched: a small fixed tool set over fixed SQL is not one, and this ADR gives it no way to become one. **Sections 3.1 and 1.1 were read and are not edited.** Section 3.1's "user-facing text is a rendering of validated data" and Section 1.1's "explicit negative outcome instead of a plausible unsupported answer" are read as claims about this system's own output — the tool result, and the page and API that render it — which they remain true of; text a host model writes beyond the tool boundary is outside both claims, and item 3 is where that is stated. A reader who needs the cross-reference finds it in the Section 3.3 sentence, which is the one place the Charter names the boundary.
- **The Milestone 4 gate item that judged the export closes with it.** Charter Section 9's Milestone 4 gate reads "exported values are derived from the normalized runtime result"; [api-v0.1](../contracts/api-v0.1.md) Section 8 assigns that item — `G1` — to `export-v0.1`, which is not in this tree and is served by no route. Moving the deliverable out of scope leaves that item with no deliverable, no owning contract and no evidence, so it closes with the deliverable rather than standing unmet: the Milestone 4 acceptance record cites this ADR for it instead of recording a fail or dropping it silently. `G2` and `G3`, which `api-v0.1` Section 8 owns, are unaffected. Restoring the export restores the gate item with it. **Two `api-v0.1` rows close with this ADR under Path B:** the Section 8 row "The #169 decision point on export", which names an ADR under Charter Section 10 as Path B's record and says Milestone 4 does not close before one is recorded — this is that record; and the Section 9 deferred row "Serving an export", which says Path B "moves TSV export out of Milestone 4, and this row closes with it".
- **The `mcp-v0.1` contract** is the next slice, under the [Contract Shape Framework](../contracts/README.md), with the line budget #169 Decision B set. Its acceptance evidence is the equality cases in item 1 above; its Section 9 carries the reading of Decision A this ADR amends; it registers that `/v1/ask` is not a tool (item 5); and it carries the `limitations` wording patch item 4 assigns to it, as the `entity-discovery-v0.1` Section 10 patch the owner records there.
- **`api-v0.1`** is amended in its own slice to retire `/v1/ask` and `proposal` from **the documented path** — item 5's wording, and not from the public route table. This bullet read "from the public route table" when the ADR was recorded, which was stronger than item 5's "no longer the path a reader is directed to" and "This ADR does not remove them"; the repository owner decided on [#203](https://github.com/OKJ1105/evidence-first-rag/issues/203#issuecomment-5827589592) to keep the route and retire it from what a reader is pointed at, so the stronger wording is superseded. The page's Ask panel goes with it; the discovery and selection panels stay. **Two statements elsewhere still carry the superseded reading**: [mcp-v0.1](../contracts/mcp-v0.1.md) Section 3.2, which calls the retirement "an `api-v0.1` Section 10 amendment … not this document's", and its Section 9 row, which holds the retirement open as the repository owner's. Both are now decided against by #203 and are the owner's to close as a patch under that contract's Section 10, on its own slice; no reader should take either as a retirement still to come.
- **Milestone 4 closes** on the acceptance record, which states #195's fail, #193's registered-but-unrunnable rows, and this ADR's Path B honestly. **Milestone 5** deploys the same runtime with the MCP endpoint beside `/v1`; the Milestone 5 gate's "no second schema, fixture meaning, SQL-template behavior, or fallback runtime" is what makes the equality cases in item 1 the right acceptance evidence.
- **The link.** The Milestone 4 record on #169 (2026-09-21) placed "the MCP question" after Milestone 5 because "a host-configured MCP server is not a link". This ADR supersedes that ordering, and the reason is the primary source above: a page whose backend calls the Messages API with `mcp_servers` set is a link, and its response carries the tool results as typed blocks the page can render beside the model's text. That page belongs to the portfolio site's repository and is named here only so the goal's link is accounted for. Readers with a Claude or ChatGPT client add the server as a connector; readers with neither read a recorded transcript in the README.
- **The standing hazard is the one item 3 names**, and it is a hazard of the host, not of this runtime. Observed use is the evidence for whether it is realised; if it is, the owned-loop alternative above is the recorded next step, and nothing built under this ADR is discarded by it.
